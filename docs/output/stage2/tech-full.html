1. 项目概述与建设目标

「长安智策」是面向西安市的城市决策空间智能平台，以 自然语言交互 + 空间地理可视化 为核心，覆盖 市民民生、游客文旅、企业全生命周期、小微商户、政府治理 五大业务域，共计 99 项功能。

当前已交付的版本为 高保真可交互原型（纯静态 HTML/CSS/JS，前端 mock 数据）。本技术文档描述的是将原型 工程化为可上线生产系统 的完整技术方案，明确前后端如何实现、数据库如何设计、数据从何而来。

建设目标

  • 99 项功能全量后端化，数据实时可更新
  • 意图识别由前端规则升级为后端 NLP 模型
  • 空间地理数据接入真实底图与 GIS 服务
  • 双端（PC 工作台 / 移动 App）统一服务
  • 支持账号体系、权限分级、后台运营

建设范围

  • 5 大端 99 项功能模块
  • 6 类展示模式引擎（A–F）
  • 意图识别与多轮对话
  • 地图/GIS 空间服务
  • 用户中心、后台管理、数据治理
关键认知：原型中的「AI 回复话术」「空间点位」「图表数据」当前是前端写死的 mock。生产系统中，这些数据必须来自后端数据库与真实数据源，由接口动态下发。这是本文档与「静态原型」的本质区别。

3. 技术选型与理由

3.1 前端

类别选型理由
框架Vue 3 + TypeScript生态成熟、上手快、适合政府/企业级中台；TS 保障 99 项模块的类型安全
UI 组件库Element Plus（PC）+ Vant（移动）PC 工作台与移动 App 双端统一风格，减少自研成本
状态管理Pinia轻量、与 Vue3 深度集成，管理 module/device/view 三态
地图引擎高德地图 JS API（或腾讯位置服务）真实底图、逆地理、路线规划；政府项目常用且合规
图表ECharts 5柱/条/雷达/折线/环形/堆叠全支持，替代原型自研 SVG 引擎
构建Vite秒级热更、产物优化

3.2 后端

类别选型理由
主语言Java 17 + Spring Boot 3政务/企业主流、生态完整、团队招聘容易
微服务Spring Cloud Alibaba（Nacos 注册/配置 + Gateway + OpenFeign）国产化、与政务云适配好
NLP 服务Python 3.11 + FastAPI意图识别模型（深度学习）生态在 Python 侧最成熟
模型BERT/RoBERTa 中文预训练 + 微调（或通义/文心大模型 API）短文本意图分类精度高；预算充足可用大模型增强泛化
接口风格RESTful（对外）+ gRPC（服务间）对外通用，对内高性能

3.3 数据层

数据库用途理由
MySQL 8.0业务主库（模块、点位、流程、政策、指标）事务、成熟、运维成本低
PostgreSQL 14 + PostGIS空间数据（点位坐标、热力、路径、空间查询）空间函数强、支持地理索引，是空间计算的事实标准
MongoDB 6对话记录、用户方案、非结构化 JSON模式 D/E 的图表/仿真 JSON 结构天然适合文档存储
Redis 7热点缓存、车位余量、会话、限流高频读写（如实时余位）需内存缓存
MinIO / 阿里云 OSS图层瓦片、导出 PDF、影像对象存储承载大文件
为什么原型里的数据要「一拆为四」？ 原型把「空间点位 + 业务属性 + 图表 JSON + 话术」全塞在一个 JS 对象里。生产系统必须拆开：点位坐标进 PostGIS（要做空间查询）、业务属性进 MySQL（要做事务和关联）、图表/仿真 JSON 进 MongoDB（结构多变）、热点余量进 Redis（要毫秒级读）。这是从「能显示」到「能生产」的关键差异。

4. 核心业务流程设计

4.1 双端路由逻辑（从原型抽象为正式状态机）

原型中通过 state.device（pc/app）与 state.cur（当前模块）解耦，实现「同一模块双端对等切换」。生产系统需将其固化为 后端路由规则 + 前端状态机：

用户进入 → 后端下发角色清单/首页配置
    │
    ▼
输入需求 / 点击模块 ──► intent-service 识别意图
    │                    │ 返回 moduleId + confidence + role
    ▼                    ▼
按 state.device 分流：
  ├─ pc  → module-service 生成「三栏结果集」→ 前端渲染工作台
  └─ app → module-service 生成「对话结果卡片」→ 前端渲染对话流

双端切换（switchDevice）：
  保持 moduleId 不变，仅切换渲染形态，后端同一接口复用

4.2 六大展示模式的数据契约

这是数据库与接口设计的核心依据。原型中 99 项功能按 6 类模式组织，每类模式的 中间展示区 字段契约如下（生产系统据此建表与接口）：

模式适用场景中间区字段契约对应端示例
A 空间地理类点位查询、分布、路线map{layers[], legend[], pois[]} + cards[]市民C01 停车、C05 快递柜
B 办事流程类办事指引、证照steps[]（环节/机构/时限/材料/注意） + map.pois[]市民C02 年检、商户证照
C 政策清单类政策匹配、补贴cards[]（金额/条件/窗口/依据） + map企业E 政策、游客优惠
D 分析评估类评估、体检、短板kpi[] + table{cols,rows} + charts{hbar,line,donut...} + map{heat,pois}政府G02 环卫热力、G 评估
E 仿真推演类内涝、客流、风险panel[] + sim{frames[]（时间/kpi/pois/heat）}政府G07 内涝、游客客流
F 台账统计类台账盘点、普查summary + table{cols,rows} + map政府G 台账
设计原则：无论哪种模式，右侧决策区（KPI 指标、分析洞察、可执行动作）契约统一为 right{kpis[], insights[], actions[]}。这保证前端有一个稳定的渲染引擎，后端只需按模式填充不同字段。

5. 数据库设计

5.1 设计总览

业务主库 MySQL 承载「模块、角色、点位、流程、政策、指标」等结构化数据；空间坐标与空间分析交由 PostgreSQL+PostGIS；对话与方案等非结构化 JSON 存 MongoDB。

5.2 MySQL 核心表结构

① 模块表 sys_module（99 项功能的主表）

CREATE TABLE sys_module (
  id            VARCHAR(16)  PRIMARY KEY,          -- 模块编号 C01/T04/E01/G07/M09
  role          VARCHAR(20)  NOT NULL,             -- 端: citizen/tourist/enterprise/merchant/gov
  name          VARCHAR(128) NOT NULL,             -- 模块名称
  mode          CHAR(1)      NOT NULL,             -- 展示模式 A-F
  alias         JSON         NOT NULL,             -- 意图关键词数组 ["停车","车位","违停"]
  ask           VARCHAR(256),                      -- 示例提问话术
  reply         TEXT,                              -- AI 默认回复话术
  follow_ups    JSON,                              -- 推荐追问数组
  sort_order    INT DEFAULT 0,                     -- 排序
  status        TINYINT DEFAULT 1,                 -- 1上线 0下线
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_role (role), KEY idx_mode (mode)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='功能模块主表';

② 空间点位表 geo_poi（模式 A/B/C/D/E/F 通用）

CREATE TABLE geo_poi (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id     VARCHAR(16)  NOT NULL,             -- 归属模块
  name          VARCHAR(128) NOT NULL,             -- 点位名称
  zone          VARCHAR(64),                       -- 所属片区（曲江/小寨…）
  kind          VARCHAR(20),                       -- 点位类型 traffic/risk/warn/gov/biz/service/med/green/park
  big_flag      TINYINT DEFAULT 0,                 -- 是否重点标注
  hot_flag      TINYINT DEFAULT 0,                 -- 是否热点
  label         VARCHAR(64),                       -- 地图短标签
  desc_text     VARCHAR(512),                      -- 点位描述
  lng           DECIMAL(10,6) NOT NULL,            -- 经度
  lat           DECIMAL(10,6) NOT NULL,            -- 纬度
  info          JSON,                              -- 详情键值对 [["总车位","400"],...]
  sort_order    INT DEFAULT 0,
  KEY idx_module (module_id), KEY idx_kind (kind)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='空间点位表';

③ 流程步骤表 flow_step（模式 B）

CREATE TABLE flow_step (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id     VARCHAR(16) NOT NULL,              -- 归属模块
  step_no       INT NOT NULL,                      -- 步骤序号
  title         VARCHAR(128) NOT NULL,             -- 步骤标题
  dept          VARCHAR(128),                      -- 办理机构
  duration      VARCHAR(32),                       -- 时限
  materials     JSON,                              -- 所需材料数组
  note          TEXT,                              -- 注意事项
  KEY idx_module (module_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='办事流程步骤表';

④ 政策条目表 policy_item（模式 C）

CREATE TABLE policy_item (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id     VARCHAR(16) NOT NULL,             -- 归属模块
  title         VARCHAR(128) NOT NULL,            -- 政策/补贴名称
  amount        VARCHAR(64),                      -- 金额/优惠
  condition     TEXT,                             -- 申报条件
  window       VARCHAR(128),                     -- 申报窗口/渠道
  basis         VARCHAR(256),                     -- 政策依据
  tag           VARCHAR(32),                      -- 标签（推荐/风险/策略）
  desc_text     TEXT,
  KEY idx_module (module_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='政策清单条目表';

⑤ KPI 指标表 decision_kpi（右侧决策区，全模式通用）

CREATE TABLE decision_kpi (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id     VARCHAR(16) NOT NULL,
  kpi_key       VARCHAR(64)  NOT NULL,            -- 指标名
  value         VARCHAR(32)  NOT NULL,            -- 指标值
  unit          VARCHAR(16),                      -- 单位
  delta         VARCHAR(64),                      -- 变化说明
  cls           VARCHAR(16),                      -- 涨跌样式 up/down/flat
  KEY idx_module (module_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='决策指标KPI表';

⑥ 洞察与动作表 decision_insight / decision_action

CREATE TABLE decision_insight (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id VARCHAR(16) NOT NULL,
  title VARCHAR(64) NOT NULL,                      -- 洞察标题（余量判断/风险判断）
  body TEXT NOT NULL,                              -- 洞察正文（含HTML高亮）
  KEY idx_module (module_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分析洞察表';

CREATE TABLE decision_action (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_id VARCHAR(16) NOT NULL,
  title VARCHAR(64) NOT NULL,                      -- 动作名
  gesture VARCHAR(16),                             -- 跳转/展开/开启/预约/下载/办理
  KEY idx_module (module_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='可执行动作表';

5.3 PostgreSQL + PostGIS 空间表

CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE geo_point (
  id BIGSERIAL PRIMARY KEY,
  module_id VARCHAR(16) NOT NULL,
  kind VARCHAR(20),
  geom GEOMETRY(Point, 4326) NOT NULL,            -- WGS84 坐标点
  props JSONB,                                     -- 业务属性
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_geo_point_geom ON geo_point USING GIST(geom);
CREATE INDEX idx_geo_point_module ON geo_point(module_id);
为何坐标单独进 PostGIS？ 原型用「相对坐标 x/y 锚定」在 SVG 里画示意图。生产系统要支持 真实经纬度、周边搜索、距离计算、热力聚合、空间范围查询（如「1km 内停车场」「3km 内医院」），必须用 PostGIS 的 ST_DWithin、ST_Distance、GiST 空间索引。真实坐标可用高德/腾讯地理编码将地名转为经纬度。

7.3 数据治理要点

  • 统一标准：所有点位统一转为 WGS84 经纬度 + GCJ-02（高德）双坐标存储
  • 质量校验：字段完整性、坐标范围校验（西安行政区划内）、重复去重
  • 数据血缘：每条数据标注来源、采集时间、版本，可追溯
  • 合规：政务数据需取得授权；地图需符合国家测绘合规要求（正确使用审图号、边界）

8. AI 意图识别引擎设计

8.1 方案选型

方案技术适用成本
方案一（推荐）BERT/RoBERTa 中文预训练模型 + 99 分类微调意图明确、领域固定中（需 GPU 训练 + 推理）
方案二大模型 API（通义千问/文心一言）RAG泛化问答、开放描述按量付费，需知识库
方案三（过渡）规则 + 关键词（原型现有方案）快速上线、兜底低（无需训练）
推荐组合：以微调模型做主识别（精准、快、可控），大模型做兜底与多轮澄清（处理长尾表达），规则引擎做缓存与兜底。三层串联，兼顾精度、成本与上线速度。

8.2 训练数据准备

99 项功能，每项需准备训练样本：

  • 正样本：模块的 alias（关键词）+ ask（示例问句）+ 人工扩写 20~50 条同义表达
  • 负样本：易混淆模块间的对照样本（如「停车」vs「违章停车处罚」）
  • 样本量建议：每模块 50~100 条，总量 5000~10000 条

8.3 置信度与多轮对话

  • 模型输出 softmax 概率 → 映射为 0~99 置信度（原型 62~99 区间）
  • 置信度 < 阈值（如 70）时，触发澄清追问（返回 top-3 候选让用户确认）
  • 多轮对话上下文存 MongoDB dialog 集合，支持指代消解

9. 空间地理服务设计

9.1 地图引擎

原型用自研 SVG 示意底图（城墙/环线抽象）。生产系统替换为 高德地图 JS API（或腾讯位置服务），支持：真实底图瓦片、缩放平移、点标记、热力图、路线规划、逆地理编码。

9.2 图层与坐标

项说明
坐标系WGS84（存储）→ GCJ-02（高德展示），需坐标转换
点位图层按 kind 分类（traffic/risk/warn/gov/biz/service/med/green/park）渲染不同图标与颜色
热力图层heat 数组 → 高德 Heatmap 图层
仿真图层内涝淹没范围 → 半透明多边形随时间帧切换

地图合规（重要）：中国地图必须使用经审核的地图服务，不得使用未审图号的自绘地图；涉及行政区划边界、国界线必须准确。需使用具备互联网地图服务资质（甲级测绘）的厂商，并正确展示审图号。这是政府项目的硬性合规要求。
